## 0. 结论摘要

**整体方案可行，适合按三层分步推进**：元素级可收藏（底层机制）、预制组件（内容供给）、白板收藏夹（容器与编辑器）。

| 需求 | 可行性判定 | 主要依据 |
| --- | --- | --- |
| 收藏夹作为「可自由排布的白板」 | **基础完备**，改造量中等 | 今日页已是可配置卡片板，具备 `HomeCard`、`col: main/rail`、`off` 持久化及上下/跨栏移动能力（`state/homeOrder.ts`、`pages/Today.tsx`） |
| 预制组件（文字/标题/按钮/数据卡/分隔线/入口） | **可行**，工作重心在数据接线 | 各类数据 hook 已就绪（`useCard`、`useCampusData` 及课表/作业/通知各自的 hook），组件外壳可直接复用 `HomeCard` |
| 点阵网格 + 长按拖拽 + 其余项自行让位 | **可行**，是本需求的核心工程量 | 长按拖拽可直接复用现有实现（`components/useNavDrag.ts`），其余项让位配合仓库已有的 FLIP 位移动画即可完成 |
| 元素级「所见即所得」收藏 | **可行，采用声明式 widget 路线** | 现有收藏按**页面**登记（各页将 `collect.item` 注入菜单），升级到元素级只需扩充一套轻量声明与注册机制 |
| 编辑导航栏（显隐/调序/自定义入口） | **基础完备**，改造量中等 | 栏目管理弹窗已支持勾选显隐、↑↓ 调序与恢复默认（`components/TabManageModal.tsx`）；PC 侧栏偏好存取也已就绪（`loadSidebarPrefs` / `resolveSidebar` / `saveSidebarPrefs`） |
| 用收藏夹替换今日页 | **可行**，且与现有架构同构 | 今日页本身即是按角色排序的卡片板，将其纳为系统预制的默认 board 即可平滑演进 |

**首要设计决策**：明确元素级收藏的实现语义。围绕需求原文提出的「看到什么收藏了之后还是什么（按钮收藏了之后还是这个按钮原封不动）」，对比三条技术路线后结论如下：

| 路线 | 做法 | 判定 |
| --- | --- | --- |
| A 声明式 widget（**推荐**） | 由开发者为可收藏元素声明一份 widget 规格（类型 + 属性），收藏夹使用同一份组件实现重新渲染 | 真正实现所见即所得（同组件、同属性），天然支持多实例、跨页与离线使用；代价是每个可收藏元素需补充一份轻量声明 |
| B 抓取 DOM 快照 | 收藏时序列化元素当时的 DOM 外形 | 仅保留静态外观、**无法交互**，数据停留在快照时刻，切换字体或主题时易错位，难以承载原子操作 |
| C 传送真实节点 | 将源页面上的真实节点 portal 到收藏夹 | 单个节点无法在两处同时挂载，源页面卸载后即失效，也无法创建多实例 |

本文后续章节均基于路线 A 展开。

## 1. 需求解读

将需求原文拆解为六个可落地的施工模块：

1. **组件判定标准**（原文给出 10 个例子）：自身具备完整上下文，且能独立完成一项（或一族）原子操作的元素才算组件。全量页面元素的组件判定表见本文第 7 节。
2. **元素级可收藏**：任意页面上的组件均可收藏，收藏后保持原有形态与交互（同组件、同属性）。
3. **预制组件**：涵盖文字标签、文字标题、跳转按钮、数据卡片（校园卡余额 / GPA / 学分 / 剩余作业 等）、分隔线与跳转入口，并支持补充新类型。
4. **收藏夹即白板**：支持自由排布、调整部分组件的样式、添加预制组件，内部统一记录每个组件的属性与网格位置。
5. **三种使用形态**：替换今日页（今日页本身即系统预制的收藏夹）、作为自定义界面挂载进导航栏（导航栏支持编辑显隐、图标与名称，「我的」常驻保留），以及作为常规收藏夹使用。
6. **编辑模式**：提供点阵背景、组件锚点吸附点阵、长按拖拽，以及其余组件自动让位。

## 3. 数据模型（白板文档 v1）

设计原则：**一块白板对应一份本地文档，版本号先行**。整体延续仓库既有的本机存储范式（与 `hwRemind` JSON、`tabLayout`、`SidebarPrefs` 一致），保持零外部依赖与纯本地读写。

> **实现期细化（2026-10-09，P0 开工时实测）**：既有今日页布局**按窗口朝向分别持久化**
> （`onethu.home.layout.portrait` / `…landscape`），PC 端窗口宽窄切换时会读取对应朝向的布局。为延续原有观感，
> `Board` 的单元格集合调整为**按朝向各存一份**（`cells: Partial<Record<HomeOrientation, BoardItem[]>>`）；
> 用户自建白板默认写入 `portrait`，宽窗口下按 §6.1 的比例规则映射。下文模型已按此同步。

```ts
interface BoardDoc {
  v: 1;                       // 版本号，迁移用
  boards: Board[];            // 至少一个（系统预制的「今日」）
  activeBoardId: string;      // 当前主页用哪块板
}
interface Board {
  id: string;                 // 稳定 id，导航入口引用它
  name: string;               // 用户可改
  icon: string;               // 图标名（走既有图标集）
  kind: "system" | "user";    // 系统板（今日）不可删
  items: BoardItem[];
}
interface BoardItem {
  id: string;                 // 实例 id（同一 widget 可多实例）
  spec: WidgetSpec;           // 渲染什么（见第 4 节）
  cell: { x: number; y: number; w: number; h: number };  // 点阵坐标，单位=格
  props?: Record<string, unknown>;  // 用户可调（文字内容、显示项等）
  pinned?: boolean;                 // 「固定」：正常模式下长按不进入快捷编辑（编辑模式仍可长按）
}
```

设计要点：

- **以网格为存储单位**：`cell` 统一记录**基准格单位**（手机端 4 列为基准；PC 端 8 列对应每单位 2 列，换算规则见 §6.1），仅在渲染期换算为像素，避免设备屏幕密度与字号缩放引起布局漂移。
- **位置与属性解耦**：编辑器负责更新 `cell`，组件设置面板负责更新 `props`，渲染层只读消费。
- **版本迁移**：检测到 `v` 版本较低时按序逐级升级；`v1` 迁移负责将今日页现有的位次与显隐配置转换为一块 `kind: "system"` 的系统白板。
- **存储容量**：单条 item 约占 200–400 字节，50 个组件合计约 20KB，远在本地存储容量上限之内；写入异常时沿用仓库现有的存储错误提示，提供一键重试。
- **兼容既有原子收藏**：保留 `state/atoms.tsx` 的引用式书签，作为 `kind: "link"` 的一种 WidgetSpec 接入白板，使传统收藏夹自然融入白板体系，共用同一套界面。

## 4. 元素级收藏：声明式 widget

### 4.1 核心组成

1. **WidgetSpec**：描述渲染内容与参数的可序列化声明。
2. **Widget 注册表**：维护 `spec.kind` 到渲染实现的集中映射，供白板画布与「添加组件」面板共用。
3. **可收藏声明**：由页面元素声明自身对应的 spec 及当前实例属性。

```ts
type WidgetSpec =
  | { kind: "atom-link"; ref: string }              // 既有原子书签（页/实体）
  | { kind: "nav"; page: Page; params?: LearnNav }  // 跳转按钮/入口
  | { kind: "card"; card: WidgetCardId }            // 预制数据卡（余额/GPA/作业…）
  | { kind: "text"; text: string; variant: "label" | "title" }
  | { kind: "divider" }
  | { kind: "custom"; id: string; props: Record<string, unknown> }; // 页面自带的复杂组件
```

### 4.2 页面元素声明方式

采用无侵入的轻量包装组件，保持原有渲染结构原封不动：

```tsx
// 复杂组件（页面自带的卡片/条目）
<Collectable spec={{ kind: "custom", id: "card.balance", props: { days } }}>
  <BalanceCard days={days} />
</Collectable>

// 简单入口（按钮/行）
<Collectable spec={{ kind: "nav", page: "card" }}><button>校园卡</button></Collectable>
```

`Collectable` 的职责非常精简：

- 在容器上挂载 `data-collectable` 属性与运行时可读的 spec（保存在局部状态即可，无需放入全局 store）；
- 将「收藏此组件」注入该元素的菜单：桌面端响应右键、移动端响应长按（直接复用现有的上下文菜单宿主与 `useNavDrag` 长按判定）；
- 触发收藏时，将 spec（连同用户在设置中调整过的 props）追加写入目标白板。

借由**同一份组件实现与同一份属性参数**，组件收藏到白板后天然保持原貌与完整交互。

### 4.3 组件判定的三条标准

1. **上下文完整**：脱离所在页面单独出现时，用户依然清楚它的含义与作用对象。例如仅有「充值」「下载」二字的孤立按钮，或缺少说明的下拉菜单，因缺少独立上下文而留在原页面内使用。
2. **能独立完成原子操作**：点击或交互行为可独立闭环（如页面跳转、提交动作、切换某项设置），无需依赖原页面的其余区域；纯视觉装饰元素归入非组件。
3. **可独立实例化**：仅凭一份属性参数即可从零完整渲染，无需依赖兄弟节点状态或所在列表的滚动位置。

展示型卡片（如 GPA 卡、余额卡、学生卡）按第 2 条标准同样归为组件：**信息展示**本身即其独立完成的原子操作，与需求原文对「显示 GPA 的卡片」的界定一致。

### 4.4 注册策略：两档成本与七项定义

**覆盖范围（霖 2026-10-09 确认）**：本轮将第 7 节判定表中归为组件的元素**全量注册**（约 40–50 个）。

**昂贵档本轮策略（霖 2026-10-09 确认）**：优先**复用现有卡片外壳**——今日页的 `HomeCard` 本身具备独立卡壳，这些复杂卡片本轮先沿用原页面卡壳接入白板，后续批次再将卡片内核进一步抽离为独立组件。

| 档位 | 适用对象 | 实现方式 | 成本 |
| --- | --- | --- | --- |
| 便宜档 | 具备完整上下文的入口（服务行 / 导航按钮 / 列表项） | 外包一层 `Collectable`，spec 设为 `nav` 或 `atom-link`，白板端统一由通用入口卡渲染 | 低 |
| 昂贵档 | 复杂卡片（课表卡 / 余额卡 / GPA 卡 / 学生卡 / 通知列表 …） | 支持脱离原页面独立渲染，本轮先复用现有卡壳 | 中 |

每项注册需配齐**七项定义**：

| 字段 | 用途 | 消费方 |
| --- | --- | --- |
| `kind` / `id` | 注册表主键与 `spec` 引用 | 渲染层、白板文档 |
| `title` | 「添加组件」面板中的显示名称 | 添加面板 |
| `description` | 长按菜单中的**详情**说明 | 组件菜单 |
| `render(props)` | 独立渲染实现（昂贵档核心） | 白板 |
| `defaultSize` + `sizeRange` | 初始占格与允许尺寸范围（如课表卡最小占格约束） | 编辑器 |
| `editableProps` + 表单声明 | 长按菜单中的**编辑**抽屉（无可编辑项时自动隐藏该入口） | 编辑器 |
| 可序列化上下文 | 收藏时写入 `spec.props` 的引用参数 | `Collectable` |

**两项落地约定**：

- 按第 7 节全表推进覆盖，**以页面为单位拆分为多个执行单元**（每个单元按「代码 + 覆盖断言」一次提交、「文档同步」一次提交拆分），便于逐批复核。
- 注册组件时在**同一提交内**补齐该页面的覆盖断言（见第 11 节 `collectable-coverage`），防止后续改动误删声明。

**描述文案规范**：`description` 直接呈现在用户的长按「详情」菜单中，需采用简洁易懂的面向用户表述，并写明运行前提（例如：「校园卡余额与最近流水，需要登录」）。

## 5. 预制组件

### 5.1 类型清单

| spec.kind | 形态 | 用户可调属性 | 备注 |
| --- | --- | --- | --- |
| `text`（variant=label） | 文字标签 | 文字、字号档、颜色令牌档 | 需求原文明确要求 |
| `text`（variant=title） | 文字标题 | 文字、字号档 | 与标签独立区分，保持清晰的排版层级 |
| `nav` | 跳转按钮 | 目标页/参数、图标、文字 | 覆盖需求原文的「通往某一个页面的按钮」与「跳转入口」 |
| `card` | 数据卡片 | 显示项、时间窗（如校园卡流水天数） | 见 §5.2 数据源表 |
| `divider` | 分隔线 | 粗细档、是否带标题 | 需求原文明确要求 |
| `atom-link` | 既有原子书签 | 展示形态（行/卡） | 与现有收藏互通，见第 3 节 |
| `custom` | 页面自带的复杂组件（余额卡、GPA 卡、学生卡…） | 由该组件自行声明 | 元素级收藏的主要承载形态 |

### 5.2 数据源接线（预制数据卡片）

| 卡片 | 数据来源（现状） | 新鲜度策略 |
| --- | --- | --- |
| 校园卡余额 / 最近流水 | `useCard(days)`（`state/data.ts`） | 沿用既有 SWR：进入可见区即重验证，请求失败时保留旧值 |
| 门户聚合数据（含成绩入口） | `useCampusData()` | 同上 |
| 课表（今日/本周） | 今日页已有的课表数据链（可复用 `homeOrder` 时段判定） | 同上 |
| 剩余作业 / 作业提醒 | 作业页与提醒链（`hwRemind`、作业 hook） | 同上 |
| 通知 | 通知页数据链 | 同上 |
| GPA / 学分 | 信息页成绩栏目数据链 | 同上；取数开销较大时先读本地缓存，进入可见区再后台刷新 |

**取数规范**：按霖确认的口径，白板**可在 state 层新增取数 hook，统一读取既有接口与缓存**——直接复用信息页等模块已有的数据链路，延续「我的」页的请求边界。若某张卡片缺少现成数据链路且无法在 state 层拼装，则回退为「跳转入口」形态。

### 5.3 补充建议（需求原文开放拓展）

- **快捷动作卡**：将「打卡/签到」等高频操作通过 `custom` 封装为可收藏组件，一步直达目标动作。
- **空态引导组件**：当画布删减至仅剩少量组件或为空时，展示「添加组件」引导卡片，保持白板观感完整自然。
- **起步模板**：内置 2–3 套预设排版（如「课表 + 作业 + 通知」「余额 + 日程」「极简模式」），方便用户一键套用后再按偏好微调。
- **文本导入导出**：将白板文档序列化为文本以便复制分享，可直接复用插件市场的仓库分享机制。

## 6. 白板与编辑模式

### 6.1 布局模型：网格吸附与跨端换算

需求明确了「背景点阵 + 锚点吸附」、**预设尺寸档位**（1x1 / 1x2 / 2x2 / 2x1 / 1x3 / 2x3 …）以及**宽度上限 4**（铺满页面内容区，含页边距）。据此定案网格规格：**手机端 4 列 / PC 端 8 列**（霖 2026-10-09 补充确认），行数按内容向下自然延伸。

**坐标基准（核心约定）**：文档中的 `cell` 统一以**手机端 4 格为基准单位**记录，需求原文的「宽度最大 4」同样基于该基准。渲染期按当前设备换算：

| 设备 | 物理列数 | 1 个基准单位 = | 最大宽度 |
| --- | --- | --- | --- |
| 手机 | 4 列 | 1 列 | 4 单位（顶满，含页边距） |
| PC | 8 列 | 2 列 | 4 单位（= 8 列，顶满） |

由此同一块白板在双端**保持一致的排版比例**（手机端的 1x1 对应 PC 端的 2x2 物理列），一份布局数据即可同时驱动手机与桌面端；PC 端的吸附点阵以「2 个物理列为一格」，与手机端网格一一对应。未来若需开放 PC 端半格精度，只需引入第二套基准并补充版本迁移。

| 方案 | 评估结论 |
| --- | --- |
| 格布局（**已定案**） | 让位规则清晰确定、天然契合点阵吸附、跨设备比例一致（手机 4 列 / PC 8 列按基准单位换算），组件排布整齐对齐到格点 |
| 自由坐标 | 摆放位置虽然任意，但防重叠让位与跨端缩放复杂度高，手摆组件也极易因微差产生视觉参差 |

### 6.2 渲染与让位

- **渲染定位**：渲染顺序与文档顺序一致；每项按 `cell` 绝对定位，统一采用 `transform: translate(...)` 驱动位移，避免布局重排抖动。
- **拖拽与实时让位**：拖拽途中被拖项跟手移动（逐帧更新 `transform`），其余组件按**目标格**实时重排，并通过 FLIP 动画平滑过渡（记录旧位置 → 更新目标格 → 读取新位置 → 施加反向偏移 → 过渡归零），与仓库既有的跨栏让位实现同源。
- **松手写入**：拖拽期间仅修改内存状态，松手定稿时一次性将最新 `cell` 写回文档。
- **落位规则**（按二次补充需求定稿）：组件**直接落在松手所在的网格坐标**，保留上方或中间的留白区域，支持任意纵向跨度（如坐标 `(1,1000)`）。
- **让位规则**：仅在**重叠**时触发让位——落点与既有组件重叠时，被覆盖的组件**自动向下顺延**（霖 2026-10-09 定案，对齐安卓桌面交互），拖拽期间实时预览让位结果，松手即定稿。

### 6.3 编辑模式交互

| 操作 | 入口 | 复用 |
| --- | --- | --- |
| 进入/退出编辑 | 收藏夹页面右上「···」菜单中的「编辑」 | 既有页面级菜单机制 |
| 长按 → 拖拽 | 长按先弹出**组件菜单**，手指产生位移后升级为拖拽（编排见 §6.5） | `components/useNavDrag.ts` 的长按与位移判据 |
| 调大小 | 选中后拖动**四边拖拽点**（需求定稿）；尺寸档位 1x1 / 1x2 / 2x2 / 2x1 / 1x3 / 2x3 …，宽度上限 4 单位 | 新增；约束到格，松手写回 `w×h` |
| 删除 | 选中后点击删除按钮，或拖入删除区 | 新增 |
| 组件设置 | 选中后点击「设置」→ 弹层修改 `props` | 既有弹层范式（同时接好 Esc 与返回键，落实 §28.14 经验） |

### 6.4 移动端与老引擎注意事项（WebView 96）

- 拖拽期间仅修改 `transform` 与 `opacity`，`will-change: transform` 仅在拖拽激活态挂载，松手后立即移除。
- 点阵背景使用单层 CSS 径向渐变平铺（`background-image: radial-gradient(...)` + `background-size`），无需创建额外 DOM 节点。
- `touch-action: none` 仅加在可拖拽项上并在拖拽结束后立即移除，保持常规浏览时的顺畅滚动。
- 长按与滚动互斥：手指移动超过阈值即取消长按计时（与导航拖拽共用同一套判据）。
- 开启减弱动效时：其余组件让位直接一步到位，拖拽过程保持实时跟手。

### 6.5 编辑态视觉与长按编排（按二次补充需求定稿）

进入编辑态（右上「···」→「编辑」）后：

| 元素 | 编辑态表现 |
| --- | --- |
| 背景 | 固定间距点阵（由单层 CSS 渐变平铺生成） |
| 组件 | 较正常浏览态**略微内缩**，四边露出背后的点阵网格（正常态边框自然覆盖点阵） |
| 点击组件 | 直接呼出该组件的操作菜单（编辑态下暂缓组件自身的业务点击） |
| 进入/退出 | 带有平滑过渡动画（点阵渐显，组件尺寸与位置柔和过渡） |

正常浏览模式下的长按编排（交互手感对齐安卓桌面小组件）：

1. 长按达到阈值 → 弹出**该组件的长按菜单**，同时触发一次轻触感反馈（沿用仓库既有触感分级）；
2. 手指继续产生位移 → 本次手势平滑升级为**移动拖拽**：长按菜单自动收起，其余组件**模糊 + 渐隐 + 略微缩小**，当前拖动的组件**保持原尺寸**，背景点阵**渐显**辅助对齐；
3. 拖拽期间**实时预览松手后的排版布局**（含其余组件让位结果）；
4. 松手定稿 → 组件落入目标网格，界面**自动复原至正常浏览模式**（点阵淡出、其余组件恢复清晰）。

实现要点：长按判定与「位移升级」阈值直接复用 `components/useNavDrag.ts` 的既有实现（超出位移阈值即取消长按并转入拖拽）；模糊与缩放仅更新 `filter`、`opacity` 与 `transform`，点阵显隐通过 `opacity` 过渡；开启减弱动效时点阵直接显现、其余组件即时让位。

```ts
  slots: Array<{ id: string; kind: "page" | "board"; page?: Page; boardId?: string; icon: string; label: string; hidden?: boolean }>;
}
```

核心要点：

- **默认配置与现状一致**：首次启动解析出的槽位与现有五项完全相同，编辑前界面观感保持原样，随时可平滑回退。
- **「我的」常驻保留**：在解析器中强制确保「我的」槽位始终存在且可见（承载全局设置入口），并配套自动化护栏测试。
- **自定义白板挂载为槽位**：`kind: "board"` 槽位直接渲染目标白板，图标与名称读取自该 board 的 `icon` 与 `name`。按霖确认的口径，**除「我的」外的其余槽位**（今日 / 待办 / 服务 / 收藏）均可替换为自定义白板。
- **归属规则同步升级为槽位级**：`navOwner` 原先按固定页面归属，引入自定义白板槽位后需扩展为按「导航槽位」归属，确保 E6「任意页面恰好高亮一项」与返回键归属继续准确运作。该改动涉及全局导航链路，建议单独划为一个执行单元推进，并专项复查 E6 相关护栏。

### 8.2 与今日页的关系

今日页当前由 `HomeCard` 加位次/显隐表驱动。升级方案将其**统一纳为一块 `kind: "system"` 的系统白板**：

- 首次启动：根据现有位次与显隐表生成该系统白板（迁移逻辑见第 3 节），底层继续复用 `HomeCard` 渲染，视觉观感与卡片顺序平滑延续；
- 用户编辑后：改动直接写回 board 文档，今日页与其他白板共用同一套编辑与持久化能力；
- 「用收藏夹替换今日页」：将 `activeBoardId` 指向用户自建白板，今日槽位即刻展示目标白板；系统默认白板依然保留在收藏夹列表中，随时可切回。

### 13.8 霖报的四个现场 bug：定位与修复（第三轮）

四个现场问题均已在真机复现并修复。实测读数采自 K90（myron / Android 16 / WebView 143，APK md5 `0ef73266991b7c7f18600d9ad7421b53`），卡片流同时在兼容性基线 K30 Pro（Android 12 / WebView 79）上复核通过。

**① 收起抽屉后顶栏右上角「···」消失。** 取证时间线显示：抽屉展开时页面内共有 **4 个 `.page-head`**、顶栏 `more=true`；收起抽屉后 `.page-head` 回到 1 个，顶栏却变为 `more=false`。根因在于抽屉预览渲染了**真实卡体**，网络学堂搜索等卡体内部自带 `PageHead`，挂载时将空菜单写入全局 `pageChrome` 并接管 owner，卸载时又将全局 chrome 清空，而底层白板页未触发重渲染，导致顶栏持续读到空菜单。修法：让 `PageHead` 自动识别自身是否处于预览容器内（`.add-preview-box` / `.widget-size-box` / `.add-drawer`），预览实例在同步与卸载清理两处均直接跳过；同时为 chrome 快照补充**菜单内容签名**，提交后做一次对账回填。修复后展开与收起抽屉全程保持 `more=true`。

**② 抽屉内容被挤成顶部窄行、下方大片留白。** 根因在于底部圆点指示栏受移动端全局规则 `button { min-height: 36px }` 影响被撑高至 36px（即问题 ④），导致展开态内容总高度超出 56vh 上限而挤压变形。修复问题 ④ 后各段尺寸恢复正常：抽屉高 451px / 卡片流 180px / 指示栏 6px / 确认按钮 38px。

**③ 卡片流从右向左滑动时偶发反向跳闪。** 根因在于卡片节点原先以「距前台的相对槽位」作为 React key，当 `pos` 跨过半格阈值时，各节点的**绑定档位与位移量同时跳变一格**，视觉上如同整条卡片流反向闪动。修法：改为按**绝对档位索引 `p`** 生成稳定 key，使相对位移 `p − pos` 全程连续变化。实测跨过半格时三张卡片平滑跟手移动 30px（与手指位移一致），松手后「已选」顺畅由 1×1 切至 2×1。

**④ 指示栏圆点被纵向拉成椭圆。** 根因在于手机端全局样式 `button:not(.switch):not(.plg-switch) { min-height: 36px }` 选择器优先级 `(0,2,1)` 高于 `.widget-size-dot` 的 `(0,1,0)`，单独声明 `min-height: 0` 被覆盖。修法：使用 `.widget-size-dots[data-size-dots] button.widget-size-dot` 将优先级提升至 `(0,3,1)`。实测指示栏高度恢复为 6px，普通圆点 6×6，当前选中圆点经 `scale(1.6)` 放大后为标准 10×10 正圆。

**同轮并入改进**：为「余额速览」补齐**自足卡体**（此前依赖今日页发布快照，首次直接进入白板时会显示「内容由原页面提供」），并按定稿实现两档排版（4×1 横向并排 / 4×2 上下两行、左名称右数值）；入口行说明文字按宽度分档展示（4 宽完整说明 / 3 宽截取「·」后短句 / 2 宽显示「进入」 / 1 宽隐藏说明），同时补齐了此前缺失的 `wg-entry-name / hint / chevron` 样式规则。

**护栏**：`topbar-chrome` 新增「预览内 PageHead 跳过全局 chrome」「仅清理自身 token」「内容签名短路」断言；`board-edit` 新增卡片撑满槽位与预览、入口行样式、卡片流容器与指示栏断言；`board-templates` 新增余额速览自足卡体与双档排版、入口行按宽分档断言。

### 13.9 第四轮：指示栏被确认按钮压住 + 中等力度一挥反向（待真机复核）

**⑤ 指示栏被确认按钮遮挡。** 根因在于竖向空间紧凑时，卡片流原本带有固定 `min-height: 180px` 无法压缩，且 `.widget-size-picker` 未裁剪溢出，超出高度便向下滑入确认按钮底部。修法：将卡片流设为**唯一弹性伸缩段**（`min-height: 0`），标题行与指示栏保持固定高度，并为 picker 增加 `overflow: hidden`（极端窄高屏幕下优先收敛卡片流高度，确保指示栏完整保留）；同时将展开态高度由 56vh 上调至 60vh，微调预览基准单位（30 → 28）、方框（128 → 116）与卡片高度（176 → 156），使主流机型无需触发裁剪即可完整容纳。

**⑥ 中等力度左滑停在两项之间时偶发退回上一格。** 根因在于松手瞬间的初速度原先仅取**最后两帧差值**：手指收势抬起瞬间常伴随轻微回弹，导致末两帧速度方向与整段滑动手势相反，进而把惯性投射翻转为反向（轻滑与快挥不易落入该临界区间，唯独中等力度滑动恰好触发退一格）。修法：改为计算最近 **120ms 滑动窗口**的平均速度，并增加方向一致性校验——若惯性投射方向与整段手势净位移方向相悖，则忽略瞬时投射、直接按净位移方向吸附。

**待真机补测说明**：本轮修复安装至 K90 后停留在登录页，暂未在真机界面上跑完自动读数（前四项 ①②③④ 已在 K90 / K30 完成取数）。**人工复核步骤**：打开「添加组件」→ 选择任一档位组件 → 确认底部三枚圆点完整露在「添加 / 修改大小」按钮上方且无遮挡；随后按住卡片流以中等力度向左挥动并在松手前轻微回弹，确认卡片**顺畅前进一格**，向右执行相同动作则平稳后退一格。

**护栏**：`board-edit` 新增「卡片流为唯一弹性伸缩段（`min-height: 0` + picker `overflow: hidden`）」与「松手速度采用时间窗均值（`samples` / `<= 120`）+ 投射方向与净位移同向校验（`Math.sign(fling) !== Math.sign(net)`）」断言。

### 13.10 第五轮：两项列表的倒演 + 指示栏下沿被压（待真机复核）

**⑦ 仅有两个档位时，左滑后偶发「向左倒演回第二项」。** 根因在于**补间动画途中重设目标**：拖动将 `pos` 从 1 推向 2（切往下一档）并通知父组件后，父组件将 `index` 置为 0，而此刻过渡中的 `round(pos)` 仍处在 1；同步 effect 检测到数值差异，立即调用 `gotoIdx(0)` 按「最短路径」计算目标，在 `n = 2` 正反等距时取到了 `-1`，导致刚完成的前进手势**反向倒演回去**（唯独慢速拖到底使 `round(pos)` 提前到达 2 时可避开，与霖现场观察一致）。修法：引入 `animRef` 状态锁，**在补间动画与手势拖拽期间保持当前运动轨迹**，待动画收尾后再与最新目标档位做一次对齐。

**⑧ 指示栏下沿与确认按钮轻微叠压。** 修法：为 `.widget-size-dots` 分配独立的 14px 高度（6px 圆点 + 上下各 4px 余量）并设置 `position` 与 `z-index`，使当前选中圆点经 `scale(1.6)` 放大后依然稳居容器之内，即便出现 1px 级盒模型贴合也能完整绘制在上方。

**待真机补测说明**（设备停在登录页，原因同 §13.9）。**人工复核步骤**：选用包含两个档位的组件（如「余额速览」的 4×1 / 4×2）→ 从第一项左滑切至第二项 → 再次左滑，确认卡片**沿原方向继续前进回第一项**且动画连贯自然；同时确认圆点指示栏上下边缘完整清晰。

### 13.11 第六轮：整体卡顿（已按真因拆掉两处放大器）

霖 2026-10-12 现场反馈：打开抽屉后界面整体卡顿明显，页面稍向上滑动即出现掉帧抽搐。

**真因一：抽屉预览区的全子树 `MutationObserver`。** 该监听器最初用于拦截异步挂载的输入框（首帧 41 个、3 秒后增至 44 个），监听了 `childList + subtree`，每次回调都会全量重扫 `.add-preview-box / .widget-size-box` 及其整棵子树。由于抽屉总览同屏挂载了 **51 个真实卡体预览**，卡体内部的数据 hook 持续触发重渲染与 DOM 变更，引发高频全量重扫并占满主线程；上下滚动时的父级布局变化又进一步放大了这一开销。

**真因二：`PageHead` 每次渲染注册 `setTimeout` 自愈同步。** 该定时器最初用于兜底全局 chrome 被意外清空的场景，自 §13.8 从源头隔离预览区 `PageHead` 后，该兜底已成为纯额外负担（长页面上每次渲染周期均会产生定时器调度）。

**修法**：将抽屉预览区的输入框禁用处理精简为挂载时**单次批量扫描**（通过复合选择器一次性设置 `disabled` 与 `tabIndex`），后续异步挂载的输入框直接交由既有的 `focusin` 监听兜底失焦（§13.7 实测已证明该链路在 WebView 96 上独立可靠）；同时直接移除 `PageHead` 中的补同步定时器。

**待真机补测说明**（K90 停在登录页，待登录后复核）。**人工复核步骤**：打开「添加组件」上下滑动总览网格，确认滚动顺滑无抽搐；点入任一组件详情左右滑动卡片流确认跟手流畅；同时验证全流程未误拉起系统输入法。

**护栏**：`board-edit` 新增反向断言禁止抽屉内再次引入 `new MutationObserver`；`topbar-chrome` 新增反向断言禁止出现按渲染周期调度的补同步定时器。

### 13.12 第七轮：确认键「点两次才生效」（霖补的触感线索直接指到真因）

霖 2026-10-12 现场反馈：点击「修改大小」首次无响应，且**第一次点按连触感振动都未出现**，点第二次才生效。

**触感线索直指根因**：全局触感反馈（`lib/haptics.ts` 的 `installGlobalHaptics`，见该文件 §L213）注册在捕获阶段的 `click` 事件上——首次点击**未产生触感**，直接表明浏览器底层该次触摸并未合成出 `click` 事件，回调自然无从触发。此前使用 CDP 直接派发合成 `click` 验证时绕过了真机触摸合成链路，因此未能提前暴露。

**修法**：在保留鼠标 `click` 路径的同时，为确认按钮增设**指针直达路径**：`pointerup` 命中按钮且按下位移 ≤12px 时立即触发确认动作，并与 `click` 共用 400ms 一次性防重入闸门；指针路径通过 `preventDefault()` 拦截随后可能到达的合成 `click`，同时主动补发与 `.btn` 一致的 `haptic("tick")` 触感反馈；桌面鼠标点击则继续沿用全局触感委托，确保单次操作只振动一次。此外为确认按钮设置 `position` 与 `z-index: 2` 置于档位区上方，配合档位区 `overflow: hidden`，消除边缘 1px 重叠抢占点按的隐患。

**待真机补测说明**（K90 停在登录页，待登录后复核）。**人工复核步骤**：长按任一组件 → 点击「改变大小」→ 抽屉展开后**单击一次**「修改大小」，确认单次点击立即生效并伴随触感反馈；随后在「添加组件」流程中验证确认按钮同样一次响应。

**护栏**：`board-edit` 新增「确认按钮具备指针直达路径 `activate(true)` 与一次性闸门 `firedRef`」「指针路径主动触发 `haptic("tick")`」「确认按钮设置 `z-index: 2` 位于档位区之上」三条断言。

**后续观察项**：总览网格一次性挂载 51 个真实卡体本身也存在一定基础开销。若移除上述两处性能放大器后低端设备仍有轻微掉帧，下一步可单独立项，将总览预览优化为**进入视口后再按需挂载真实卡体**（视口外先展示轻量骨架）。

## 15. 预览数据层：抽屉预览不再现爬数据（2026-10-12）

### 15.1 问题与做法

抽屉中的组件预览直接复用了**真实业务组件**，挂载时会各自调用 `useCard`、`useReport`、`useCampusData` 等 hook 拉取数据——导致用户打开抽屉挑选组件时连带触发全量数据爬取，并将个人真实数据显示在预览卡片上（霖 2026-10-12 明确要求：预览区统一展示静态示例数据，避免现场拉取真实接口）。

利用全部 13 个业务 hook **共用同一份 SWR 模块级缓存**的架构特点，无需逐一侵入修改各个 hook 的内部逻辑，直接在缓存层统一注入预览示例即可干净拦截请求：

1. `state/cache.ts` 新增 `cacheSeedPreview(key, data)`：将示例数据写入内存缓存，并将**时间戳设为远未来**（`Number.MAX_SAFE_INTEGER`），使 `Date.now() - at` 恒为负数、缓存永不过期，从源头避免发出任何真实请求；抽屉关闭还原时将原有缓存条目原样放回，保持真实业务缓存与本地持久化纯净无污染。
2. `state/cache.ts` 同步提供 `setPreviewMode / isPreviewMode`：多数 hook 遵循「缓存命中且未过期即直接复用」的规则（预置缓存即可拦截请求），唯独 `useLearnData` 采用**挂载即刷新**策略，且 `useNews` / `useTodayNewsFeed` 的**缓存键带有动态参数**，需配合预览开关显式跳过拉取。将该开关置于底层叶子模块后，数据层与预览层均可直接引用，保持单向无环依赖。
3. `components/PreviewData.tsx` 提供 `PreviewDataProvider`：**先在 `useLayoutEffect` 中注入全部示例数据并将 `ready` 置为真，随后再渲染 `children`**。这一执行顺序至关重要——子组件的 `useState(() => cacheGet(...))` 发生在首次同步渲染阶段，而普通 `useEffect` 按「先子后父」顺序触发；先完成缓存注入再挂载子树，可确保子组件首屏即读到示例数据且全程零请求发出。
4. `components/BoardAddDrawer.tsx`：将抽屉整棵预览子树（总览网格 + 档位预览）统一包裹在 `PreviewDataProvider` 之内。
