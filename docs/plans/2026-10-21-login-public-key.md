# 0.11 登录公钥报错、重复认证与设备指纹修复


> 归档说明：本文记录当时的设计方案与阶段性验收情况；0.11 现行功能与使用说明请查阅 [文档入口](../README.md)（[English overview](../en/index.md)）。

用户反馈 Android 0.11 在多次登录或刷新后出现 `Failed to get public key.`，且账号信任因子接近上限时也会遇到同类报错。本轮集中修复主登录链路中可复现的客户端缺陷，并补充脱敏诊断信息以便定位学校认证端在特定网络与风控下的实时响应。

## 已确认的问题

1. `currentFingerprint()` 返回实际参与认证的设备指纹，而 `persist()` 却可能写入 `CampusSession` 构造器另行生成的随机指纹——首次登录或快照中仅有指纹尚无 cookie 时尤为容易触发。离线直接调用原函数即可复现两者不一致，进而造成设备身份与信任凭据错配。
2. 客户端遇到任何登录报错都会立即用同一组凭据重跑一遍完整登录，导致密码错误、公钥解析异常乃至 HTTP 429 限流均被连发两次。原有的 20 秒冷却仅保存在内存变量中，手动登录入口未做拦截且页面刷新即清零，库内自动恢复路径同样会绕开该计时。
3. 免密确认接口返回带正常公钥的登录表单页时，`passwordlessEntry()` 会直接丢弃该页面并返回 null；确认请求自身的网络错误与 HTTP 异常状态码也被吞没，最终统一表现为获取公钥失败。
4. 登录完成后的业务漫游阶段即便收到已登录成功页，仍会强制尝试提取公钥并抛出同一异常，使得单凭该报错难以区分“凭据尚未提交”“漫游已成功”与“访问受限”等不同阶段。
5. 当 2FA 会话过期触发静默重建认证链时，用户刚输入的验证码会在新验证码 hook 就绪前丢失；动态口令（TOTP）路径也存在同样的等待时序竞争，且重发验证码失败时仍会误提示“已发送”。

## 修复内容

- 统一同步 helper、`CampusSession` 与持久化快照中的设备指纹，确保尚无 cookie 的初始快照也能准确恢复同一设备身份。
- 移除界面层的无条件二次重登，并为登录提交加上同步互斥锁；在库内新建登录链的 admission hook 中统一校验并记录 20 秒冷却，随后再清理认证域 cookie。复用进行中的认证链或继续完成 2FA 时跳过清仓与冷却计时；冷却时间戳写入 `sessionStorage` 以跨当前 WebView 刷新生效，全程不存储账号或密码凭据。
- 保留免密确认返回的凭据登录页，单次登录最多执行一次确认 POST 加一次凭据 POST，并将底层网络错误与 HTTP 状态码原样向上传递；收到成功页或 2FA 页时直接衔接到对应状态。
- 限定确认表单仅能提交至 HTTPS ID 主机白名单内的已知认证端点；公钥提取同时兼容标签文本与 `input value`，并校验椭圆曲线点合法性。
- 为未知页面、缺失公钥、信任设备达上限、访问受限、异常表单与确认死循环建立稳定的错误分类，配齐中英文界面提示；学校服务端明确返回的错误正文则原样呈现。
- 等待新验证码 hook 就绪后再提交验证码，若认证链已彻底失效则明确提示重新发起登录。同一验证方式重发验证码时真实调用 `SEND_CODE`，切换其他已绑定验证方式时引导重新登录；发码失败如实报错，并在提交或发码请求进行期间锁定返回操作以稳住当前 UI。后台已在等待输入的 2FA 会话按 `attemptId` 与账号精确接管，避免重放上一轮方式或串入其他账号凭据。
- 信任设备达到上限时维持“当次验证照常通过，仅跳过保存新信任凭据”的既有策略，保留用户原有的已信任设备记录；提示文案支持自动换行并展示 8 秒。新签发的信任凭据实时同步至水合缓存，防止后续读回旧票据。
- 在登录与 2FA 报错区域新增“复制诊断”按钮；当系统剪贴板受限时自动展开可供手动选中复制的诊断文本框。
- 登录诊断严格仅记录 HTTP 状态码、脱敏路径、响应字符数与所处阶段，绝不写入响应 HTML 正文、cookie 值或用户凭据。

## 回归定位

新版诊断日志中，`AUTH-FAIL reason=… stage=…` 直接标明认证失败原因与所处阶段，`ILIB status=… final=… chars=…` 辅助核对重定向落点与页面体量，所有 URL 查询票据均自动剥离。后续若用户再次遇到同类报错，只需复制这段脱敏诊断摘要即可协助定位，全程无需提供密码、验证码、cookie 或认证网页原文。
