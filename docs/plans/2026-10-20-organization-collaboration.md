# 组织权限与多人协作（2026-10-20）


> 归档说明：本文记录当时的设计方案与阶段性验收情况；0.11 当前功能与使用指南请查阅 [文档入口](../README.md)（[English overview](../en/index.md)）。

围绕组织成员、角色权限、项目与公告落地真实的多人云端协作机制，解决此前仅在本地维护名单缓存、移除或降级成员后未在服务端同步回收访问权限的问题。

## 架构决定

直接依托现有的清华 GitLab 私有群组与专属私有元数据仓库承载协作状态，无需额外部署自建后端。本地既有组织可通过点击「启用多人协作」完成显式迁移：已有的项目与公告自动上传至远端，尚未绑定 GitLab 账号的历史成员名单则保留为待绑定记录。接收组织分享口令仅用于定位目标组织，实际读写访问须通过 GitLab 群组成员授权验证。

- 成员真实身份与角色统一以 GitLab 当前登录用户及群组成员 API 返回结果为准，本地 `onethu.orgs.v1` 仅用于保存界面缓存与远端仓库关联引用。
- `onethu-admin/organization.json` 存放组织基础资料、成员云盘邮箱绑定、关联资源清单及待收尾的权限变更记录。服务端受保护分支配置为仅允许 Maintainer 及以上级别推送；同时 OneTHU 受管群组仅开放 Owner（50）、Developer（30）、Reporter（20）三档角色，拒绝 Maintainer（40）及元数据仓库层面的额外单独授权，从而在服务端层面确保只有组织 Owner 具备管理配置分支的写入权限。
- `onethu-content/collaboration.json` 存放项目与公告内容，对应受保护分支允许 Developer 与 Owner 推送写入，Reporter 保持只读访问。
- 每次从远端拉取状态时，客户端均会逐项核验仓库私有性、所属群组归属、是否存在外部群组共享或直接成员越权、以及受保护分支规则（含通配符规则及指定用户/群组/Deploy Key 例外）；一旦发现安全基线偏离即阻断写入，严格以服务端实时权限为准。
- 打开组织页面、窗口重新获得焦点以及页面处于前台可见状态期间每 30 秒自动向服务端同步最新状态，提交任意数据修改后也会立即回读确认。

## 并发与故障

文件写入统一携带 GitLab Repository Files API 的 `last_commit_id` 做乐观并发校验，编辑提交前还会比对原始条目快照，防止无意覆盖他人的并发修改或删除；一旦发生版本冲突，界面会完整保留用户刚输入的内容，引导刷新比对后再提交。初始化协作遇到网络重试且远端已存在合法配置文档时，仅校验归属关系并直接回读，避免用本地旧缓存覆盖远端状态。群组与元数据仓库路径均由组织 ID 确定性派生：若建仓请求响应中途丢失，重试时会先按固定路径查回既有资源，且同一页面内的初始化请求采用单飞复用，杜绝连点创建重复仓库。

每次权限调整都遵循「先将待办操作记入受保护管理配置 → 依次更新服务端群组成员与关联资源 ACL → 回读核实全部生效后清除待办记录」的三段式闭环。若中途任一环节失败，界面会完整展示异常明细并提供「重试未完成的权限变更」入口，如实反映当前进度，直至全部子步骤核实完成后才宣告成功。

- 变更前预先审计关联的清华云盘资料库：操作人必须为资料库所有者；若检测到独立群组共享、全员共享、子目录单独共享或公开分享链接等旁路访问通道，会先行拦截变更并提示负责人清理旁路，确保后续撤销个人共享时能够真正收回访问权。
- 关联的 GitLab 代码仓库必须位于本组织的私有群组名下，且无外部共享群组或未知的直接授权成员，拒绝接入 public/internal 仓库或外部命名空间仓库。组织内新建仓库默认锁定为私有，云盘资料库仅分发需登录认证的成员深链，全程杜绝生成公开链接。
- 迁移存量云盘资料库与代码仓库时同样须完整通过上述安全审计与 ACL 对账，全部达标后方写入 `permissionsVerified` 标记；若尚有未达标项则明确列出具体原因并维持待迁移状态。
- 新增资源关联时先校验全体成员的云盘邮箱与目标资源 ACL，再落盘保存权限待办记录。存在未完成待办时，支持补充或修正成员云盘邮箱、或是主动解除问题资源关联，并全程追踪所有曾尝试授权的邮箱以便彻底回收因响应超时遗留的半程授权；待办收尾前锁定角色调整与新成员添加，保持恢复流程清晰可控。
- 新增成员或调整角色：逐一对齐并回读核实 GitLab 群组、关联代码仓库及云盘资料库三端权限。
- 移除成员：同步撤回群组及全部关联资源的访问授权；若检测到因上级父群组继承等原因导致无法由本级直接剥离访问权，会明确报错指出继承来源，协助负责人彻底排查。
- 更换成员云盘邮箱：严格按照「先撤回旧邮箱权限，再授予新邮箱权限」的顺序执行；若某一处撤权失败，会继续尽力完成其余已审计资源的撤权与降权动作，并立即中止后续一切新增授权；若前置安全审计未通过，则直接中止，零权限改动。
- 云盘资料库所有者天然持有最高控制权，若需将其降为只读或移出组织，须先在云盘完成资料库所有权移交。
- 解除组织资源关联时，自动清退由本组织直接下发的成员授权，资源原有的所有者归属及外部群组继承关系保持原貌。
- 服务端强制至少保留一名组织 Owner，防止当前唯一负责人将自己降级或移除后留下无人可收尾的悬挂操作。

鉴于 GitLab 与 Seafile 为两套独立系统、不存在跨服务的底层原子事务，本方案通过受保护分支内的持久化操作日志与幂等目标状态对账实现可靠的最终一致性。若其他负责人直接在 GitLab 或云盘网页端手动变更了成员权限，OneTHU 刷新后会自动对齐最新实际权限或清晰提示状态差异。

## 验证与真实边界

- `node --import ./tools/ts-resolve-register.mjs tools/org-collaboration-test.mjs`：38 条协议层自动化测试全部通过，基于内存模拟服务端覆盖撤权、降级、更换邮箱、网络中断重试、幂等恢复、服务端拒绝、父群组继承权限检测及 CAS 提交冲突。
- `node tools/org-collaboration-browser-test.mjs`：25 条端到端断言全部通过，启动两个独立浏览器上下文配合模拟服务端 ACL/CAS 引擎驱动真实 `orgSync`，完整验证存量组织迁移、多人协同读写、越权写入拦截、并发编辑冲突、成员降级与移除、页面重载恢复，以及缺邮箱迁移补填、历史尝试邮箱回收、不合规资源预检拦截与初始化响应丢失恢复。
- `tools/lib/fake-org.mjs` 提供纯本地内存态的 GitLab 协议模拟，全程零真实账号与线上资源读写。
- `node tools/org-collaboration-live.mjs --run-isolated`：预留线上真实实例联调脚本，读取环境变量 `GITLAB_TOKEN`（及可选的第二账号 `GITLAB_SECOND_TOKEN`），仅新建带唯一标识的独立私有测试群组并在验证完毕后自动请求清理，全程隔离现有业务仓库且隐去敏感令牌输出。
- 当前本地环境暂未注入 GitLab API 测试令牌，且尚无第二个测试账号；待令牌与双账号就位后，可直接执行上述 live 脚本完成真实清华 GitLab 实例写接口与跨账号授权/撤回联调。
