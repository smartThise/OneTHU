# 好友邀请接收、资料库删除与刷新按钮恢复


> 归档说明：本文记录当时的设计方案与阶段性验收情况；0.11 当前功能与使用指南请查阅 [文档入口](../README.md)（[English overview](../en/index.md)）。

日期：2026-10-20。分支：`dev3`，基线 `6ec1061b`。按用户当前安排暂缓生成 APK。

## 问题与方案

早期好友通道仅实现了发送端的本地记录与共享文件夹创建，缺少接收端的自动发现与绑定流程；同时 Rust 侧 `seafile_repos` 将 `virtual=true` 的共享子目录全部过滤，导致接收方无法看到他人共享过来的资源，且旧版留言功能只支持写入、缺少读取展示。

新方案直接利用学校 Seafile 既有的指定账号共享机制传递邀请，无需额外部署应用服务器。新建好友通道时仅向目标云盘邮箱授予读写权限，告别公开分享链接；受邀账号在自己的共享库根目录读取轻量邀请清单，核对云盘返回的所有者、收件人及权限匹配无误后，一键即可接入同一资料库，省去反向建库或二次交换口令的步骤。

## 已实现

- 完整模式下在应用启动、切回前台、恢复联网时立即检查邀请，并在前台驻留期间每 30 秒轮询一次；应用切入后台隐藏后自动暂停检查，关闭期间收到的新邀请会在下次打开应用时拉取呈现。
- 顶栏与竖直标签栏均展示待接入信封计数，通讯录内提供手动检查、接入与忽略操作。收到邀请时仅提示待处理请求，由用户主动确认接入后才添加联系人，且通道清单内仅写入昵称与云盘账号标识，完整个人名片留在本地。
- 接收方确认接入后会向共享库写入回执，发起方状态随之从“等待对方接入”更新为“已连接”。
- 历史共享子目录在接收端保留各自的虚拟资料库 ID，并以根目录 `/` 作为接收路径，避免误用所有者的主库 ID 与子目录路径。
- 旧版通道点击“补发邀请”即可平滑升级；若检测到历史公开链接，会先弹窗请用户确认撤销旧链接，再写入指定账号邀请，原有文件与历史留言均完整保留。
- 忽略状态按投递版本号记录，对方重新补发后可再次提醒；重试发送会自动复用已建好的资料库。若双方各自发起了通道，可在确认后统一挂载到其中一个通道，原通道映射归档至 `previousShares`，已有云盘文件继续保留。
- 好友留言改用独立的 JSON 清单、唯一消息 ID 与专属附件目录，支持双向拉取留言与下载文件；打开通道期间每 15 秒自动刷新，切回前台时也会同步刷新，并提供手动刷新按钮。同时兼容读取早期 TXT 留言与文件，防止同名附件相互覆盖。
- 消息与邀请状态均按账号和通道严格隔离；注销、使用同一 Token 重新登录、切换账号或中途切换通道时，延迟返回的旧响应会自动丢弃。云端共享清单中可由协作者修改的作者字段仅作展示用途，真实身份核验以云盘接口返回的权限与账号为准。
- 资料库卡片与库内详情页新增删除按钮，前端与 Rust 后端双重校验所有权，仅允许删除当前账号本人拥有的非虚拟资料库；仅有 `rw` 共享权限的协作库保持不可删除状态。
- 删除前弹窗明确说明库内文件与共享访问的清理影响，若资料库已关联组织还会一并列出组织名称；删除失败时保留原列表，删除成功后清空对应缓存并刷新视图，私密分享专用清理命令的权限边界保持不变。
- 云盘深链支持经过安全校验的 `cloudRepo + cloudPath` 参数，点开好友共享文件可直接定位到目标目录，后台自动刷新时也会稳住当前浏览路径。

## 用户追加：强制刷新按钮消失

排查发现旧代码通过 `!simple` 条件控制强制刷新按钮，导致极简与实用模式下完全未挂载该控件；完整模式下还存在首次挂载未校正历史越界坐标及负坐标的问题。

现已改为三种模式均常驻保留强制刷新按钮；在加载历史手动位置、窗口尺寸变化及控件自身尺寸变化时自动将其约束在可视区域内，同时保留自由拖动与位置持久化。拖动边界计算已扣除滚动条宽度，消除左侧边缘裁切误差；每次新按下时清除上一次拖动遗留的点击抑制标记，确保拖动结束后的下一次点击正常响应。

随后针对用户反馈的“点上没反应”，进一步定位到按下微抖误判：旧逻辑在任一坐标轴移动超过 3px 时就会吞掉点击事件，日常鼠标点击出现 4px～6px 轻微位移便无法触发刷新。现已将拖动触发阈值上调为鼠标 10px、触摸 12px，达到阈值前保持按钮静止且不改写保存坐标；同时保留指针按下捕获（pointer capture），快速拖出小按钮边界时依然能顺畅跟手，自动避让逻辑也会避开用户正在按下的时段。配套补充了 2/4/6px 微抖点击与键盘触发回归测试。

本轮联调时发现 `127.0.0.1:5180` 未在监听，导致 dev App 重载页面不可达，已通过独立进程拉起 Vite 并确认返回 HTTP 200。同时修正了 `dev-app.sh`：构建装壳完成后先结束同路径下的旧版 dev 进程再启动新版，解决了原先单纯调用 `open` 只会唤醒旧进程、导致新增 Rust 命令无法生效的问题。

## 现场回归：OH-Memory 重复建库与删除按钮消失

起初怀疑是旧版原生接口缺少元数据，随后对真实云盘执行只读排查还原了真实原因：学校 `/api2/repos/` 接口实际返回的是 `type: "repo"` 与 `"grepo"`，而此前测试夹具模拟的是 `"mine"` 与 `"shared"`。由于 Rust 层原样透传、前端仅识别 `mine`，导致应用无法识别已有的个人资料库，进而反复新建同名空库并将删除按钮全部隐藏；旧测试夹具沿用了同一假设，因此此前测试虽全绿却未能暴露该差异。

具体修复如下：

- Rust 层通过当前 Token 请求 `/api2/account/info/` 获取真实账号邮箱，结合资料库的 `owner` 字段将 `repo` 准确归类为 `mine` 或 `shared`（`grepo` 保持群组资料库语义）；严格依据邮箱与所有者匹配判定归属，遇到缺少 `virtual` 字段的响应则保留未知状态。
- 将文件夹、暂存箱、壁纸、记忆与组织五处自动建库逻辑统一收口至 `ownedCloudRepo.ts`：归属状态未知时禁止自动建库；同一账号与库名的并发请求合并为单次查建；POST 建库响应不明确时先重查列表核实，并跨页面重载保留防重标记。
- 选库策略优先锁定唯一的非空资料库，防止误用空白副本覆盖原有非空数据；若检测到多个同名非空库且缺少可信缓存，则停止自动选择并交由用户确认。
- 遇到缺少新版元数据的旧原生进程时，界面明确提示更新并重启应用，同时将删除按钮置灰并展示原因说明，告别无提示隐藏。

真实云盘核查与清理记录：

- 逐一核验此前误建的 25 个 `OH-Memory` 资料库，确认均为当前账号所有、非虚拟库、大小 0 字节且目录完全为空。
- 征得用户明确同意后，在执行删除前二次复核了所有者、修改时间与空目录状态，随后清理了这 25 个空库。
- 重启新版 dev App 后，通过运行日志确认应用已准确命中原有的非空记忆库；再次只读列举云盘资料库，确认 `OH-Memory` 仅保留唯一主库（大小 19,177 字节）。
- 原记忆库及其他业务资料库均完好保留，全程未外发真实好友邀请。

后续具备第二测试账号时，可按以下顺序完成线上联调：双方更新至当前版本并各自连接清华云盘 → A 导入含云盘邮箱的 B 名片并发起邀请 → B 切回前台点击信封完成接入 → A 侧查看已连接回执 → 双方互发留言并上传同名附件验证防覆盖 → 新建一次性空资料库验证删除流程。历史共享文件夹通道可另行验证“补发邀请”升级，确认 B 侧挂载在自身虚拟库根路径 `/` 下；同时确认 App 完全退出重开后能正常拉取离线期间的新邀请。
