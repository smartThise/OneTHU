### 追加：导览选卡把首页选空了（2026-09-20 夜·三批）

用户反馈记录：「导览里只留了最近使用和猜你喜欢，点开今日是空的」。结合日志 `[TODAY] 朝向=portrait 主栏=[] 侧栏=[] 收起=36` 定位到成因：导览中卡片选项默认处于**全选状态**，用户原本想点选保留那两张卡片时，实际触发了取消勾选（同时逐个取消了其余卡片），最终落盘为空集。

四项改进措施：
1. **落盘兜底**：`applyTodayCards` 收到空集合时默认保留「今日概览」卡片，并记录一行 `[ONBOARD]` 日志；
2. **界面明示**：在选卡步骤标题旁实时显示「已留 N 张」，当数量归零时以醒目红字提示「今日页会没有任何卡片」；
3. **一键恢复**：当首页确实处于无卡片状态时，空白提示区直接提供「恢复默认布局」按钮，省去手动进入编辑面板的步骤；
4. **空态引导与键名修正**：两张推荐卡在无数据时展示友好的**空态说明**，让仅保留这两张卡片的用户也能看到清晰反馈；同时移除「猜你喜欢」初始列表中的无效键名 `thos`，避免推荐条目因注册表未命中而被静默过滤。

# 附：2026-09-21 批次（R21）——四条用户反馈的根因与修法

## ① PDF 手机预览回归（「0.9.0 当时可以」）

排查发现，`pdf.js` 渲染逻辑本身完好，问题根源在于**安卓环境判断分支未能命中**：`FilePreview` 原先使用裸 UA 正则（`/android/i.test(navigator.userAgent)`）识别安卓设备，但主窗口 UA 为兼容 WebVPN 票据绑定已在 `tauri.conf.json` 中设为桌面端 Windows Chrome/79，导致真机判断恒为 `false`，9 月 13 日补入的 `pdf.js` 分支始终未能执行，页面一直落入安卓 WebView 上显示空白的 `<embed>` 标签（与 `androidHost.ts` 在 R18c 修复过的缺陷同源）。

修复方案（`FilePreview.tsx` + `lib/androidHost.ts:choosePdfRenderMode`）：
- 安卓环境识别升级为多信号综合判定（联合 `UA`、`userAgentData` 与 `platform`）；
- 当内核原生支持 PDF 渲染（`navigator.pdfViewerEnabled` 为真）时优先采用显示效果最佳的 `<embed>`；其余环境走 `pdf.js` 画布自绘，并配置 **modern → legacy 两级构建兜底**（在缺少 `Promise.withResolvers` 等 API 的旧版内核上自动启用带兼容垫片的 legacy 构建）；
- 渲染异常统一写入 `[FILE-PREVIEW]` 诊断日志（可通过 `logcat` 抓取），并在界面上提供「换内嵌渲染」与「系统应用打开」两个备用入口。

回归护栏：`tools/pdf-render-mode-test.mjs`（涵盖分档断言与全 `src` 扫描，防止再次引入裸 UA 安卓判定）。

## ②③ 安卓小组件：刷新延迟 + 深色跟随

**刷新延迟成因**：在原有的「JS 计算文本、原生负责绘制」分工下，倒计时文案（如「还有 9 小时」）在快照推送时刻便已固定，后续 `updatePeriodMillis` 每 30 分钟触发重绘时读取的仍是同一段静态文本。**深色失配成因**：小组件布局与卡片背景此前写死了浅色色值。

修复方案（扩展 `widgetSnapshot.ts` 数据结构 + `OnethuWidget.kt` 重绘重算 + `WidgetTicker` 定时调度）：
- 快照行新增机器时间戳字段 `at/until/rel/loc`，快照顶层补充 `counts/titleAt` 统计与时间基准；
- 原生层每次重绘时结合**当前系统时钟**实时重算倒计时文案、正在上课高亮（加粗与副标题重排）、过期条目自动剔除（从顶部依次递补）、脚注计数以及标题日期；
- 刷新调度由「30 分钟常规自续心跳」与「最近 `at/until` 状态翻转时刻的 `AlarmManager` 精准闹钟」共同驱动（优先调用 `setExactAndAllowWhileIdle`，未获精确闹钟授权时平滑降级至 `setAndAllowWhileIdle`；设备重启由既有 `BOOT` 广播接收器接管，`refreshAll` 会自动重新排布定时任务）；
- 深色模式适配：布局色值抽离至 `values(-night)/widget_colors.xml`，卡片底板配置 `drawable-night/onethu_widget_bg`，桌面启动器重建视图时自动跟随系统明暗切换，行内富文本 `Span` 颜色也根据当前 `uiMode` 动态选取。

双端计算规则统一对齐纯函数参考实现 `state/widgetNativeRender.ts`，并由 `tools/widget-native-render-test.mjs` 提供自动化回归校验。

**续修（2026-09-25，用户拉大小组件尺寸后的两处反馈）**：「能显示的行数远少于实际拥有的空间」以及「总是显示还有 2 项」。成因在于此前行数仅按「矮 / 中 / 高」三档粗略估算并固定封顶 5 行（快照也仅携带 5 条候选），而脚注的「还有」计数直接读取了快照里预先算死的 `counts.more`。改进方案：
- 快照按 `WIDGET_MAX_ROWS`（20 条）充裕提供候选条目，原生层根据卡片**实际像素高度**逐行测量文本并尽可能铺满可用空间（通过 `fitRows` 与 `lineHeightPx` 动态计算，布局预留 20 个槽位，仅隐藏超出可视高度的剩余行）；
- 脚注前半段仅统计**卡片上实际渲染出的行数**，后半段「还有 N 项」按「有效可见行 − 已显示行 + 快照外 `counts.more`」动态得出，确保已显示条目与剩余条目之和始终等于当前有效总数，拉大卡片时「还有 N 项」也会随之实时减少。

**追加（2026-09-25，桌面端「通知里的图片无法正常显示」）**：在真机与桌面端联调定位后，确认诱因为**登录状态过期时缺少显性引导**——原生 `fetch_binary` 检测到响应落回登录页时会抛出「会话已失效，需要重新登录」（`lib.rs:1181`），但 `RichContent` 的 `catch` 块此前忽略了具体错误原因，仅将图片透明度调暗至 0.45，且仅在调试日志（`/tmp/onethu-debug.log` 或 Windows 下的 `D:\tmp\…`）中记录了请求 URL；页面级的数据会话提示链又未覆盖这条图片加载旁路，导致用户只看到破损图标而无从得知需要重新登录。修复方案：
- `catch (e)` 完整接收错误详情，同步写入图片的 `title` 悬停提示与 `log_debug` 诊断日志；
- 当识别为登录过期错误（通过 `lib/sessionErrors.ts` 的 `isSessionExpiredError` 统一匹配文本提示与 `SessionExpiredError` 实例）时，弹出一次**非危险档双按钮确认框**（2026-10-12 依用户反馈将自动消失的居中轻提示升级为常驻确认框 `confirmChoice`：采用毛玻璃卡片与主题色主按钮，贴合常规引导场景）：主按钮「重新登录」直达「设置 → 账号」页签，次按钮「忽略」就地关闭；单次浏览享有 10 秒去重与未响应防叠加保护，避免单页多张图片同时报错时重复弹窗。
回归护栏：`tools/session-img-prompt-test.mjs`（覆盖 10 种状态判定、弹窗接线与取数形态校验；轻提示原有的 `center` 档位保留在基础组件中供后续按需调用）。

**根因彻底收口（2026-10-12 真机，Android 16 / vivo V2324HA）**：补齐过期提示后继续深挖图片拉取链路，在真机上针对**同一图片 URL 对比不同请求通道**，锁定了最终根因：

| 取法 | 实测 |
|---|---|
| 直连 `https://learn.tsinghua.edu.cn/b/wlxt/common/downloadFiles?wjid=…` | 200 `text/html` **69 字节**：`<script>location.href="/"</script>`（直连域名下无有效登录态） |
| **WebVPN 包装形态** + 原生通道 | **200 `image/jpeg` 40–71 KB**（完整原图） |

原因在于网络学堂的登录态建立在 **WebVPN 包装域名**下（实测日志中 5862 条网络学堂数据请求全部经由包装域名成功返回），而通知正文 HTML 内嵌的图片 `src` 则是**直连**域名；与此同时，旧版 `fetch_binary` 固定携带 macOS UA 且仅读取 JS 侧 cookie，遇到按 UA 指纹校验票据的 `wengine` 网关时也会被判定票据失效（详见 `src-tauri/src/lib.rs` 原生通道说明）。
收口修法（集中于 `apps/desktop/src/lib/clients.ts`）：
- 图片 URL 先经 `normalizeWebvpnUrl` 消除重复包装，再按目标域名通过 `http.webVPNEncoder` 转换为包装形态，并为网络学堂请求补齐 `_csrf` 参数；
- 字节流拉取统一改走 **`nativeFetch`**（与 `http_native` 数据链路共享同一个客户端实例，自动携带原生 cookie 仓与主 WebView 一致的 UA），对外入口 `fetchImageAsDataUrl` 与 `fetchImageByUrl` 共用同一套底层实现；
- 保留 MIME 类型与体积校验，并将短响应体中包含 `location.href` 或登录页特征的返回结果统一归类为「会话已失效，需要重新登录」，与 Rust 侧 `fetch_binary` 判据保持同源，确保过期弹窗链路顺畅衔接。

真机复验（原问题复现页「欢迎阅读『国之所需…』」通知）：正文内两张二维码图片均清晰渲染，无破损图标与误报弹窗，日志中也再无图片拉取报错。**同类场景同步收口**：`components/FilePreview.tsx` 的二进制附件预览此前共享同一套旧版拉取方式（点击「预览」会误报「原生返回：会话已失效，需要重新登录」），现已同步接入 `sessionUrl` + `nativeFetch`，真机实测可正常渲染 `.docx` 文档。**Rust 侧附件下载链路也一并对齐**：`download_file` 与 `save_file_as` 共用的 `fetch_attachment` 现已改为读取公共常量 `SESSION_UA`（与 `build_native_client` 同源），并新增 `merge_session_cookies`（同名字段优先采用**原生 cookie 仓**，辅以 JS 侧 cookie 补充），前端 `downloadLearnUrl` 与 `saveLearnUrlAs` 同步接入 `sessionUrl()`。真机点击「下载」后界面提示「已下载到：系统下载/第4周-作业模板-2026.docx」，设备 `/sdcard/Download/` 目录下成功写入 17180 字节文件。（Rust 侧原有的 `fetch_binary` 暂予保留，继续服务尚未迁移的插件及雨课堂内联资源调用。）

## ④ Windows 用户端出现 127.0.0.1:5180

CI 通过 `tauri build` 打包的正式版已将前端静态资源完整内嵌，仅在运行 **dev 或手动 cargo 构建**产物时才会连接本地开发端口 `127.0.0.1:5180`（与 0.7.2 安卓端同类问题一致：由于两种构建产物内均包含该地址常量，需在运行时依据构建模式本身加以识别）。修复方案是在 `lib.rs` 的 `setup` 入口增加开发态守卫：当检测到 `tauri::is_dev()` 且本地开发服务器未就绪时，直接弹出原生对话框说明「这是开发版构建，请安装正式版」并安全退出，省去用户面对空白报错页的困惑。

## ⑤ 在线服务/体育点击 webview 无响应

逐环节静态排查确认：Rust 移动端链路异常均已向上传递（`265cc35`），Kotlin 侧 `openWebModal` 全路径均有明确返回，`openThosInApp` 与 `openVenueInApp` 遇到错误时均会弹出轻提示并自动回退至系统浏览器。本轮同时合并了分散的调用链：将 `ThosPage.openOfficial` 原先独立维护的内联打开逻辑（出错时仅写入页面状态，当顶部横幅在视野外时容易给人无响应的错觉）统一收口委托给 `openThosInApp`，全应用共用唯一一条打开链路。
**后续排查指引**：若特定机型上仍偶发点击悬挂，连接 `adb` 后点击一次并执行 `adb logcat -d | grep -E "THOS-UI|THOS-SEED|VENUE-PORTAL"` 即可快速定界——日志仅有 `[THOS-UI]` 而无 `[THOS-SEED]` 说明停留在 JS 到 Rust 的桥接调用；已有 `[THOS-SEED]` 但未弹出窗口则可定位至原生插件侧。

## 追加（09-21 下午二轮）：「跳浏览器」显性化 + 真机诊断通道

- **在线服务回退系统浏览器原因透明化**：新版包在应用内窗口打开受阻时按设计自动回退至系统浏览器，将原先静默吞掉的异常显性暴露了出来；但此前错误详情仅输出至 `logcat`，普通用户无法直接查看。本轮补齐三项改进：① 将失败原因摘要（截取前 60 字）直接展示在轻提示中；② 将 `loadRemembered` 纳入 `try` 捕获范围，避免其异常中断整条调用链；③ 将调试日志同步写入 `app_data_dir/logs/onethu-debug.log`，并在「设置 → 关于」中新增「导出日志」按钮（通过 `saveDownload` 桥接一键转存至系统下载目录），方便真机现场即刻提取完整诊断记录。
- **校内网络冷启动耗时约 20 秒排查**：耗时与 `reqwest` 默认的 20 秒超时阈值吻合，为精确定位慢在哪一环节，本轮在 `loadReal` 中加入分段计时（`LR-STAGE +ms`），并在 `http_request` 中补充逐跳状态与耗时记录（`NATIVE-HOP`），全部落盘至日志文件供一键导出分析。初步排查方向聚焦于校内网络环境下个别直连或公网端点连接挂起超时，或 WebVPN 包装链路在校内路由下的往返延迟放大。
- **与校方 Info App 的会话互通机制对照**：Info App 的 React Native 网络层与系统 WebView 天然共享同一个 `CookieManager`；本项目的等价方案是在 `openWebModal` 进入页面前注入票据、关闭页面时回写更新票据，待导出真机日志后即可精确定位票据交接的具体卡点。

## 定案（09-21 晚，用户日志已确认）

**在线服务/体育「点了没反应→跳浏览器」真因**：Kotlin 参数类 `SeedCookiesArgs` 与 `OpenWebModalArgs` 遗漏了 `@InvokeArg` 注解——Tauri Android 依赖该注解生成 Jackson 反序列化构造器并写入混淆保留规则；在开启 R8 压缩的正式版安装包中，`parseArgs` 因缺少构造器直接报错（`no Creators`），而未经过 R8 混淆的调试包与桌面端测试均表现正常。修复方案：补齐 `@InvokeArg` 注解，移除参数类中的 `lateinit` 修饰，并在 `consumer-rules` 中对整包补充混淆保留兜底。这也明确了后续新增移动端插件命令的通用准则：**所有入参数据类均须标注 `@InvokeArg`**。

**校内冷启动 20 秒根因确认**：实测日志显示校内环境下单次 WebVPN 请求耗时达 4–6.4 秒（其中 `wengine-vpn/cookie` 单步耗时 5.8 秒），而校外网络走同一链路仅需 300–500 毫秒，叠加后导致冷启动总耗时达到约 21.4 秒（漫游建链 12 秒 + 并行拉取数据 9.4 秒）。启动链路已补充 `NET-RESOLVE` 域名解析日志，用于验证 IPv4/IPv6 双栈解析下 IPv6 连接挂起回退的猜想，待结合下一份校内实测日志敲定优化方案。
