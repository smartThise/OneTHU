## 4. 认证修复结论

### 已确认的客户端问题与处理

1. 启动探测此前将学习服务错误、网关壳页面和超时统一归为“未登录”，进而可能触发已保存密码重登；现已拆分为“已验证”“明确失登”和“服务不可用”三类状态。仅在存在归属明确的账号快照时展示该账号本地视图，同时底层会话保持待验证状态。
2. 正常 HTTP 401、明确登录表单或明确失登响应继续走自动恢复路径；网关壳、限流、服务故障、缺失 CSRF 和未知 JSON 结构则保留原始错误上报，避免自动重新提交密码。手动登录、2FA 和既有服务会话建立流程维持不变。
3. 安装指纹改为共享读取与生成过程，并通过前端本地与原生镜像协同恢复；同一已知账号直接复用现有 Cookie，切换账号、归属未知及退出登录时执行清理隔离。
4. 恢复会话前先核对两份持久化账号快照，一致后再水合 Cookie 并访问学校接口；遇到归属冲突或存储读取异常时退回安全登录态，记住的凭据仅允许注入同账号会话。退出清理若发生异常会保留错误提示并移除当前账号视图。
5. 原生 Cookie 仓在完整清仓时立即推进账号代次并保存空仓。reqwest Cookie provider 在锁内校验请求所属代次，拦截迟到旧请求写回 Cookie；前端正文读取、clone 与派生种票同步校验同一代次。
6. 云盘 WebView、静默 profile 和 Token 提交流程均绑定操作起点，Token setter 同步核对凭据版本，覆盖“用户已退出、旧取票请求才开始提交”的竞态窗口。GitLab 种子写入与最终删除改为串行执行，清理完成后再次清空 TS 侧 Cookie 镜像。
7. 主认证、直接 CAS、选课恢复路径移除 `singleLogin/deviceName` 的自动附加，并过滤隐藏字段回带的同名参数；既有设备指纹和信任票继续沿用，验证码阶段由用户主动勾选保存信任设备的流程完整保留。

### 故障原因与证据边界

用户报告曾在同一时段出现 `AUTH-FAIL reason=unexpected-page stage=credential-entry` 和 `webvpn-guide len=2760`，随后自行恢复登录；这两项诊断分别采自统一认证入口与学习探测各自的响应。

本轮使用全新 CookieJar 和应用 User-Agent 发起一次匿名公开 GET 请求（未提交账号或密码），经 WebVPN、OAuth 跳转后正常取得统一认证登录表单（HTTP 200，17,524 字符，含公钥字段），确认排查时公开入口畅通。结合故障原始响应未留存及随后自行恢复的情况，推测当时出现了学校网关短时波动。

公开表单中的 `singleLogin` 表示“本次登录使用信任浏览器访问校内其他系统时不必再输入账号密码（统一登录）”，默认未勾选。客户端此前会自动携带该参数，现已取消默认附加以收敛自动授权请求与设备身份波动；至于学校服务端是否每次新增持久信任因子以及具体的去重策略，后续还需结合真实账号进一步验证。
