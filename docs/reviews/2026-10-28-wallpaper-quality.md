# 壁纸画质：本地存原图，云端备份才压（2026-10-28）

## 起因

用户上传背景图后觉得明显发糊。查落盘文件：1600 × 900、175 KB 的 JPEG。导入时统一做了「最长边 ≤1600 px + JPEG 0.82」的重编码，原始文件不保留。

这条口径是 localStorage 时代的遗留：当时图片要塞进 dataURL，5 MB 配额逼着必须压。现在图片已经走 `wallpaper_save` 落地到本机盘，约束不再成立。

## 观感为什么不对

桌面窗口 1240 CSS 像素、设备像素比 1.75，壁纸层按窗口铺满，实际需要 2170 物理像素宽。1600 的源图被放大 1.36 倍，照片类壁纸的边缘与细节会发软；叠加 JPEG 0.82 在高对比处的振铃。全屏到 2560 宽时是 1.6 倍。

附带两个副作用：透明 PNG 被压成 JPEG 后透明区域变黑（JPEG 没有 alpha 通道），广色域照片因 canvas 重编码掉回 sRGB。

## 改法

用户定案：本地不重编码，云端备份按「第二档」压。

- **导入**（[wallpaper.ts](../../apps/desktop/src/state/wallpaper.ts)）：JPEG、PNG、WebP、GIF 的原文件字节直接落盘，扩展名跟着原格式走；落盘前用 `createImageBitmap` 验一次能否解码，坏图不入库。单张上限 32 MB。其余格式（AVIF、BMP、SVG 等）与「写不进磁盘」的情形仍回落到 canvas 压缩（≤1600 px、JPEG 0.82、内联 dataURL），这条兜底只在浏览器预览或异常路径上走到。
- **云备份**（[cloudWallpaperImage.ts](../../apps/desktop/src/lib/cloudWallpaperImage.ts)）：上传前重编码一次，最长边 ≤ `min(3840, max(2560, 2 × 窗口物理宽))`；不透明图 JPEG 0.9，带 alpha 的图 WebP 0.92（先隔点采样确认真用了透明，没有就仍走 JPEG）；原图本来就 ≤1.2 MB 且尺寸不超上限时不动它，避免多丢一次代际。
- **额度**（[wallpArchive.ts](../../apps/desktop/src/state/wallpArchive.ts)）：单个媒体 12 → 16 MiB，整份备份 24 → 64 MiB；对应的失败提示文案同步改成 64/16 MiB。

存档格式仍是 v3，压缩结果只替换 `assets` 里的媒体字节，ref 结构（`asset:N` 去重）不变；还原时按 MIME 落盘成 `.webp` 或 `.jpg`，两种都在可还原白名单里。

## 验证

- `tools/wallpaper-quality-test.mjs`（新增，已加进 CI 的壁纸那一步）：本地原图分支不含 canvas、云端口径与上限、额度与中英文案一致、压缩只作用于备份资产、压缩器返回未知 MIME 时放弃压缩、视频不进压缩器、还原按 webp 落盘。
- `tools/wallpaper-sync-test.mjs`：37 项全过（额度相关用例改成按新上限构造，提示键名跟随新文案）。
- 类型检查、`i18n-test`（7700 键，0 错误）通过。

## 边界

- 已经上传过、仍是旧压缩图的壁纸不会自动变清晰：原始文件在上传时就被丢弃了，需要重新上传一次。
- 真机上的观感与云端实传未验证：本次只做了静态与存档层的验证，云盘上传需要账号授权。
- 本地单张 32 MB 的上限是为了挡住病态大文件，不是画质约束。
