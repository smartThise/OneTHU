## 已实现

### 1. 客户端归因

- Mac 的 lsof 精确 TCP 客户端记录增加 PID/UID 描述接口，原返回 true 的授权接口保持兼容。
- 保留 `-b -w -nP`，避免在 WebDAV 等挂载上执行阻塞的文件系统查询。
- 微信路径限定在本机 `/Applications/WeChat.app/Contents/`，核对 Apple 签名链、签名团队 `5A4RE8SF68` 和腾讯微信标识；进程名和 User-Agent 不能替代验证。
- 实机发现 App Store 版微信使用 Apple 应用签名叶证书，其 subject OU 不等于开发者团队。改为先验证 Apple 链，再读取签名代码的团队和标识。本机微信宿主与 network helper 均验证通过。
- Windows 增加当前用户 SID、精确 TCP 客户端 PID、当前运行路径和有效腾讯 Authenticode 检查。PowerShell 采用固定程序与编码参数，最多并行 4 个归因查询，另有有界排队；覆盖 16 个并发请求的模拟测试。

### 2. TLS 分流与学校身份约束

- 普通浏览器访问身份站时保持透明连接，保留原出口与学校证书。
- 通过签名验证的微信连接进入受限分流。共享身份只接受已登记小程序与已登记 ITS 服务的只读表单入口，且核对小程序 Referer 或官方业务来源。
- 清小搭：`wxc607b8a0063e7426`、`www.xiaoda.tsinghua.edu.cn`、ITS `d982b795884e882abfa8ff3167aeb03e`。
- 行在清华临时来访：`wx3cfa534a23db4039`、`visit.tsinghua.edu.cn`、ITS `04655f71b042b9d2d8d10cd566bd9c39`。
- 共享请求忽略客户端身份 Cookie，不把 OneTHU 身份 Cookie 交给客户端。业务票据和 JWT 仍由学校签发，客户端按官方协议兑换。
- 其他小程序、手动登录与验证请求使用无共享身份仓的原生 Cookie/Set-Cookie 交易；不因未知服务而把整个微信认证链拦成共享网关错误。该路径不读取或写入 OneTHU Cookie 仓。
- GUI 无法续接时保留官方登录路径；账号切换和退出使旧请求失效。真实二次验证由本人完成。

### 3. GUI 与后台共享身份

实际检查证明：GUI 清小搭登录成功并完成 Cookie handback 后，两个 ITS 服务仍返回 authenticated=false 的密码表单。单靠“共享 Cookie 已更新”无法承诺小程序免重复登录。因此最终实现转交未兑换的官方服务票据，而不以一次 GUI 登录成功冒充全局 ITS 会话建立。

- SDK 增加仅存在内存中的受限续接队列。队列传递服务枚举、随机请求 ID 与学校签发的单次服务票据；不传密码、验证码、长期令牌或 Cookie。票据仅存在内存与私有本机 IPC，界面状态和日志只保留服务枚举。
- GUI 在原窗口使用既有的清小搭 / 来访客户端和既有“记住密码”逻辑续接，将学校真实签发的未兑换短时服务票据转交受限后台请求；无需打开 OH 或用户 CLI 总开关。
- 队列有账号/epoch 校验、单次领取、超时、冷却和退出撤销；完成回执不能释放其他请求。
- 网关设置新增“续接微信校园登录”按钮；该按钮只准备学校身份，不登录腾讯微信账号。
- 学校确认表单移除新设备登记字段，并沿用安装指纹与已有信任因子。清小搭登录日志去掉姓名、证件号与带票据的 URL。

### 4. Windows 与手机

- Windows 新增按协议手动代理 / bypass 的 PAC 合成、准备指纹核验、CurrentUser 写入和比较恢复。PAC/WPAD 不作静态合并，保持明确拒绝和原设置保留。
- 平台能力区分已实现系统接入、进程归因、手动代理共存、原生客户端桥、LAN 和 VPN 前提。构造能力描述不会改变系统设置。
- Android / iOS 的系统代理或 VPN 原生桥尚未实现，设置中明确说明；没有开放 LAN 监听、广播代理口令或提供伪成功开关。
