# Android 学习会话、壁纸同步与平板编辑修复


日期：2026-10-22。基线：`main` / `e5b7ac13b649ae33d54c3ea8e044b7e1b675f89b`，应用版本 0.11.1。本报告记录初始 0.11.1 修复阶段；这些修复现已随 0.11.2 发布，完整来源、三端包与渠道记录见 [0.11.2 发布执行记录](2026-10-22-release-0.11.2.md)。

## 反馈与定位分析

用户提供的诊断日志显示 Android 客户端已处于 `ready` 状态，学习首页成功取回 125380 字节并解析出会话令牌，随后作业查看与提交双页各返回 2760 字节且缺少表单，最终弹出会话失效提示。同时，壁纸恢复截图显示 HTTP 403，横屏平板在浏览状态下也会直接响应白板组件拖拽。

结合现有代码逐项排查，这几处现象分别对应以下具体环节：

- Android 端携带的 Windows Chrome/79 User-Agent 来自现有的网关兼容策略，因此设备交互形态需要综合原生平台标识与触摸输入能力共同判定。
- 旧版诊断逻辑只要检测到页面含有 Wengine 注入变量便标记为 `webvpn-guide`，经网关代理的正常课程页也会命中这一特征，因此 125380 字节的首页属于正常加载的代理课程页面。
- 反馈材料未包含 2760 字节响应的原始正文，本轮通过在本地构造登录壳、网关提示页与接口异常响应，完整复现并加固了对应的错误处理路径。
- 壁纸截图中的 403 正文已被截断，难以直接区分是目录权限还是文件读取受限；修复方案在保留真实 403 权限提示的同时，改进了云端尚未上传过备份时的只读查找流程。

本次测试全部采用隔离的虚构数据、模拟传输与本机 HTTP 测试服务，未访问用户校园账户，也未读写或删除实际云盘内容。

## 一、学习会话与网关恢复

### 已确认的问题

1. 对于已经过 WebVPN 包装的地址，旧版 Cookie 引导流程可能会将网关域名直接送入引导接口；并发请求之间还会共享可变的请求目标对象，且未等待原生 Cookie 写入落盘便立即重放请求，增加了瞬时校验失败的概率。
2. JSON 解析失败时会抛出通用的 `AuthRequiredError`，而学习域恢复层原先仅识别其子类 `SessionExpiredError`。当业务接口返回登录页 HTML 时，学习域自身的轻量恢复流程会被跳过，转而触发全局重认证。
3. 作业查看与提交双页读取此前会将请求失败静默转为空字符串，缺少表单的异常页面也会进入详情解析，导致界面仅提示加载异常或无法提交。
4. 服务端故障、无效 JSON、接口限流与会话失效之间缺乏清晰区分，部分列表拉取失败时会被转为空数组，进而覆盖本地已有的完整快照。

### 当前处理

`packages/core/src/http.ts` 改为在每次请求发起时捕获独立的目标地址副本；引导前自动还原真实的业务域名、协议与路径（保留路径末尾斜杠），并将业务 Cookie 写入真实域名及对应的 WebVPN 应用路径，待原生层写入完成后再重放请求。无效 Cookie 与网关控制票据均会在入口处过滤。

学习模块的数据读取在 `LearnClient` 内统一校验 HTTP 状态码、页面类别与 JSON 结构：确认属于真实登录页或 HTTP 401 时进入学习域会话恢复；遇到 403、429、5xx、网关占位页或结构损坏的响应时则按服务异常上报。会话恢复按代次合并并发请求，同一轮并发共享恢复结果，单次请求最多自动重试一回。内部可恢复的会话异常在重试期间暂不向全局认证观察器广播，避免同时启动两套恢复流程。

作业查看页与提交页合并为原子读取单元：等待两页全部返回并通过校验后再解析详情，若触发会话恢复则在成功后一并重取双页。通知详情与各类列表同样接入这套校验逻辑——合法的空数组正常更新状态，而缺失结果容器或网络传输失败则会中止本次更新，完整保留上一次的有效缓存。

学习首页提取令牌时也会先检查服务端错误：首次加载若遇到 429、503 或网关占位页，会直接提示服务繁忙，避免因一时拿不到令牌而反复提交账号密码。课程页诊断现已明确区分 `learn-page-proxied` 与真实登录壳，并新增仅记录页面类别与字节长度的“学习响应”摘要；日志继续严格省略密码、Cookie、令牌与网页正文。

## 二、壁纸跨设备备份与恢复

### 已确认的问题

旧版壁纸备份直接上传本地壁纸配置文档，其中自定义本地图片仅以 `local:/某台设备/路径` 记录源设备上的文件路径，未包含图片本身的字节数据，换到另一台设备下载 JSON 后自然找不到对应文件。此外，旧恢复流程会先调用建库逻辑再读取固定路径，从未上传过壁纸的账户点按恢复时也会触发目录创建或缺文件报错。

### 当前格式与流程

新增可移植的 v3 备份档案格式，统一打包内置壁纸引用、壁纸库元数据以及去重后的图片或视频二进制内容，固定存储于个人云盘 `OneTHU/壁纸/onethu-wallpaper-v3.json`。采用独立文件名可防止旧版客户端读到新格式引用后误清空壁纸；云端原有的 `onethu-wallpaper.json` 保持不动，新版客户端恢复时优先读取 v3 档案，同时向后兼容早期内嵌媒体数据的旧档案。

恢复流程改为纯只读查找：在本人资料库中依次核对目录与备份文件是否存在，若尚未上传过备份则给出友好提示，若遇到真实 HTTP 403 则说明权限原因。导入前先完整校验整份档案，待全部媒体文件写入当前设备的壁纸目录后再切换壁纸配置文档；若恢复途中发生账号切换或本地壁纸被手动修改，流程会自动中止并清理本次新写入的媒体文件。

原生命令 `wallpaper_read` 严格限定仅读取应用专属壁纸目录下的规范化文件路径，拦截目录越界与符号链接逃逸；`seafile_upload_wallpaper` 直接通过内存流上传至本人 `OneTHU` 资料库的固定壁纸路径，不在磁盘遗留临时文件。单个媒体文件上限为 12 MiB，整份备份档案上限为 24 MiB；下载端同时按响应头与流式累计字节数执行限额（涵盖无 Content-Length 的分块传输），超出上限时明确提示并保留当前壁纸。

### 兼容和操作说明

- 若云端仅存有旧版纯路径备份，只需在仍保留原图的源设备上升级至新版并重新点按一次上传，随后即可在其他设备上完整恢复。
- 本轮新增了两个 Rust 原生命令，本地开发调试时需退出并重启 `pnpm --filter @onethu/desktop tauri:dev` 以加载新版原生层；正式环境升级至包含本次修复的新安装包即可使用。
- 壁纸备份与恢复继续采用设置页内的手动触发方式，复用现有的个人云盘授权体系。

## 三、横屏平板的白板编辑权限

此前白板仅根据窄屏布局宽度决定是否启用“先点编辑再拖动”的防误触锁定，导致横屏平板因视口宽度超过阈值而直接套用了桌面端的自由拖动规则。

现已将布局宽度与输入交互方式解耦：凡是 Android、iPad、支持多点触控的 MacIntel 以及主输入设备为粗指针（触摸）的环境，统一采用显式编辑模式。横屏平板在保留宽屏多列画布排布的同时，日常浏览状态下可顺畅滚动页面与点击组件内容，组件位置与尺寸保持锁定；点按“编辑”按钮后才开放拖拽移动与缩放，切换白板、旋转屏幕朝向、切换使用模式或退出编辑时自动恢复锁定。键鼠操作的桌面设备继续保持直接调整的原有体验。

基于真实 React 页面与浏览器 CDP 触摸协议完成交互验收：

- 新增平板触摸用例 22 项通过：覆盖 1280×800 视口、携带 Windows UA 的模拟 Android 平板、浏览态滚动、浏览态拖拽锁定、进入编辑态后的真实拖拽与缩放、组件点击跳转、横竖屏旋转、首页与 OnePage 切换、返回键退出编辑、模式切换及桌面鼠标回归。
- 既有手机编辑回归 30 项通过：覆盖 390px 竖屏与 844px 横屏，包含输入法弹出高度变化、编辑入口展示与英文界面控件。
- 平台交互策略 21 项及配套 CSS 解析、React Hook 调用顺序、白板撤销栈回归全部通过。
- 视觉归档：`/tmp/onethu-tablet-edit/tablet-browse.png`、`tablet-editing.png` 及同目录 `report.json`（手机回归报告位于 `/tmp/onethu-phone-edit-regression/report.json`），平板浏览态与编辑态截图均已人工核验。
